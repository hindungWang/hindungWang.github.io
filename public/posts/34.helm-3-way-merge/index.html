Helm 升级“丢”环境变量？一次彻底的三路合并踩坑实录

September 16, 2025

  • Helm
  • kubernetes

摘要

现象：helm install 时 values 与模板各写了一份 SERVER_IP env，YAML 里出现同名双份；修掉其中的 values 那份后，第一次 helm upgrade 反而把 SERVER_IP 从集群里删光了，第二次升级又恢复了。

根因：Helm 3 升级走的是三路 strategic merge patch，最终 patch 由两部分拼成：diff(旧→新) 里的删除项 + diff(live→新) 里的增改项。第一次升级时，diff(旧→新) 发现旧快照里多出一条同名 SERVER_IP（旧 2 条 vs 新 1 条），判定"用户删了"，生成 $patch: delete 且按 key 全删，把 live 里仅存的一份也带走；与此同时 diff(live→新) 里 old 与 live 完全相等（都只有 1 条），增改部分无事可做，救不回来。第二次升级 diff(live→新) 看到 live 是 0 条、新清单是 1 条，于是把它加回。

结论：“模板输出 ≠ 最终 patch”。--debug / --dry-run 只能看到模板渲染结果，真正的增删判定发生在 Helm 本地的 3-way merge 阶段。

一、现象复盘

1. 安装阶段（helm install）

由于疏忽，我在 values.yaml 里写上了 env，又在 deployment.yaml 模板里 range 了一次，结果 YAML 里出现同名双份 env：

  • 既在 values.yaml 里写了 
    env:
  - name: SERVER_IP
    value: "1.2.3.4"
  • 又在 deployment.yaml 模板里 range 了一次： 
    env:
- name: SERVER_IP
  value: "1.2.3.4"
...
- name: SERVER_IP      # 重复
  value: "1.2.3.4"
  • 运行时有效值只认后一条，同时抛警告（警告来自 kubelet 启动容器时）： 
    spec.template.spec.containers[0].env[11]: hides previous definition of "SERVER_IP"
    注意：这里的"只认一条"是容器运行时的最终取值；apiserver 里存的对象可能仍保留两份同名条目——这正是后面 3-way 合并踩坑的根源。无论 live 里剩 1 条还是 2 条（见下文 $patch: delete 按 key 删），最终都会消失。

为了消除这个告警消息，我将 values.yaml 里的 SERVER_IP 删掉，但保留了 template/deployment.yaml 里的 SERVER_IP。使用 --dry-run 可看到新渲染结果是只存在一个 SERVER_IP，符合预期。

然鹅，第 1 次执行 helm upgrade 时，k8s 中 SERVER_IP 消失了；同时 --debug 返回的渲染结果的确有一个 SERVER_IP。 第 2 次执行 helm upgrade 时，k8s 中 SERVER_IP 又出现了，符合预期。

2. 疑问

  1. 为什么第一次升级 SERVER_IP 会消失？（实际不是 env 全删光，只删了它）
  2. --dry-run=server、--post-renderer 为何也看不出"被删"的证据？
  3. Helm 到底把什么发给了 apiserver？

二、Helm 渲染与提交的三段流水线

阶段 内容 可见开关
① 模板渲染 go-template 输出完整 YAML --debug、 --dry-run、 --post-renderer
② 3-way merge 本地计算 strategic-merge-patch：diff(旧→新)的删除 + diff(live→新)的增改 无官方开关（下文给办法）
③ 调用 K8s 把 patch/apply 发给 apiserver --v=6 可打印 PATCH 体

大多数排障工具都停在阶段 ①，而可能让字段"消失"的决定发生在阶段 ②。这也是为什么"渲染有、集群无"。

三、3-way merge 到底在合并什么

1. 背景：Helm 为什么需要"三路”

Helm 管理 Kubernetes 资源时，本质上是在做一件事：把 Chart 渲染出来的 manifest 应用到集群中，并在升级、回滚时把已有对象更新到新的期望状态。

在 Helm 2 中，升级主要采用"两路"比较：

  • 上一次 Helm release 中保存的 manifest（old manifest）；
  • 本次 helm upgrade 渲染出的 manifest（new manifest）。

Helm 2 根据 old 与 new 的差异生成 patch 提交给 Kubernetes。问题是：它没有把集群中真实存在的 live state 纳入计算。如果资源在 Helm 之外被改过（kubectl edit、HPA、MutatingWebhook、Service Mesh sidecar 注入、控制器自动加 annotation/label 等），这些变化在补丁生成阶段可能被忽略或误删。Helm 官方文档明确指出，Helm 3 改进为三路 strategic merge patch：生成 patch 时同时考虑 old manifest、live state 和 new manifest Helm FAQ。

2. “三路”到底是哪三路？

Helm 3 的三路合并有三个输入：

  1. Old / Original：上一次 Helm 保存的对象声明 来自上一个 release revision 中保存的 manifest，表示"Helm 上次认为自己管理的期望状态"。
  2. Live / Current：集群当前真实对象状态 Helm 在升级时从 Kubernetes API Server 读取当前对象，表示"现在集群里实际长什么样"。
  3. New / Modified：本次 Chart 渲染出的新对象声明 来自当前 helm upgrade 使用的 chart、values、模板渲染结果，表示"这次 Helm 想把对象变成什么样"。

因此，三路合并不是简单地"new 覆盖 live"，也不是单纯"old 和 new 做 diff"。它是把 old 作为共同基线，同时比较：

  • Helm 自己从 old 到 new 想改什么；
  • 集群从 old 到 live 被别人或控制器改了什么；
  • 然后尽量只应用 Helm 本次声明的变更，同时保留不冲突的 live 变更。

3. 补丁如何生成：strategic merge patch 与 merge key

在 Helm 的 Go 代码中，对内置结构化资源，补丁生成逻辑位于 pkg/kube/client.go 附近，使用 Kubernetes 的 strategicpatch.CreateThreeWayMergePatch，patch 类型为 types.StrategicMergePatchType Helm client.go。

这个函数不是"old 与 new 两路求差、再把结果打到 live"。它做的是两个 diff 相加（源码注释原话：“patch 是 current→modified 的增改，加上 original→modified 的删除”，见 apimachinery patch.go）。

oldData     := json.Marshal(oldObj)      // 上次 release 保存的 manifest（= original）
newData     := json.Marshal(newObj)      // 本次渲染结果（= modified / target）
currentData := json.Marshal(liveObj)     // 从 API Server 读取的 live object（= current）

// 内部实际是：
//  deletions := diffMaps(old,      new)   // 只取"删除"：old 有、new 没有 → 生成 $patch: delete
//  delta     := diffMaps(live,     new)   // 只取"增改"：live 缺/不同、new 有 → 生成增补项
//  patch     := mergeMap(deletions, delta) // 两者拼成最终 patch

patch, _ := strategicpatch.CreateThreeWayMergePatch(
    oldData,
    newData,
    currentData,
    patchMeta, // 来自 OpenAPI / Go struct tag 的 patch metadata，决定 list 按哪个 merge key 合并
    overwrite,
)

这样拆成两份就明白了：

  • 删除部分 diff(old → new)：负责"Helm 想删掉什么"——old 里有的、new 里没有（或多出）的项目在这里被判为删除。
  • 增改部分 diff(live → new)：负责"让 live 收敛到 new 还缺什么"——live 里没有、new 里有的项目在这里被加回；两者都有的字段按值修改。

第二、四节里"old+new 求差 → 打到 live"只是便于理解的可视化比喻，严格来说是左右两个 diff 取并集。理解这一点，才能解释’为什么 old==new 时 patch 不为空'。

拿到这份 patch 之后，Helm 才把它 PATCH 到 apiserver（阶段 ③）。所以真正决定"增/删/改"的是阶段 ② 生出的补丁，而不是阶段 ① 渲染出的全量 YAML。

补丁里不只是"值"，还带语义操作：

  • $setElementOrder/xxx：标定列表项顺序；
  • $patch: delete：按 merge key 删除（不是按条目）；
  • value: null：清空字段。

关键点：env、containers 这类列表是按"合并键"（merge key = name）来合并的，不是按"有没有"判断的。Strategic Merge Patch 正是比 JSON Merge Patch 强的地方：它知道某些 list 应按 key 合并，而不是整体替换，所以 sidecar 场景下不会把整个 containers 数组粗暴换掉。

4. 三路合并的行为模型

可以把 Helm 3 的行为理解为四条规则：

情形 判定
字段在 Chart 中声明，且 new 明确给了值 按 new 收敛：把 live 拉回 new 的值
字段不在 old/new 中，是 webhook/controller/人工在 live 里加的 尽量保留
字段曾在 old 中、本次 new 删除了它 删除：视为 Chart 作者有意移除
删除时命中列表 merge key 按 key 全删（同名项全部移除）

规则一：Helm 声明并改变的字段，按 new 收敛

# old manifest / # live state / # new manifest
metadata:
  annotations:        metadata:
    a: "1"              annotations:
                        a: "2"     a: "2"
                        b: "3"     b: "3"

即使 new 与 old 中 a 都是 "1"，live 中的 a 被改成 "2"，三路合并仍会把 a 拉回 "1"，因为 a 是 Helm 声明过的字段。这是预期行为：你让 Helm 管理并声明了 a，Helm 就会把它收敛到 Chart 中的值 Helm issue #9937。

规则二：Helm 没声明、live 中额外存在的字段，尽量保留

如果字段不在 old/new 中，而是 live 里由 webhook、controller 或人工添加，例如 b: "3"，三路合并通常会保留它，不会主动删除。

规则三：old 有、new 删除的字段，Helm 会删除

例如 label version: v1 曾被 Helm 管理，本次 new 里消失了——即使 live 里这个 label 还在，也会被视作需要移除的 Helm 管理字段。

规则四：merge key 配不上一对一时，多出的同名项被删

这才是本文踩坑的那个分支：旧里同名 2 份、新里同名 1 份 → 旧的第 2 条成了"孤儿" → 判定为"用户不要多余的这条"，生成 $patch: delete，且按 key 把 live 里该名字的条目全部删掉。

四、回到案例：第一次 vs 第二次升级完整推演

第一次升级

三组数据：

输入 内容
旧 manifest 快照 env 列表里 2 条 name: SERVER_IP（values 一份 + 模板 range 一份）
新 manifest env 列表里 1 条 SERVER_IP（修复后渲染）
live object 1 条 SERVER_IP

按左右两个 diff 拆开看：

  • 删除部分 diff(旧 → 新)：旧里 2 条同名 SERVER_IP、新里 1 条 → 多的那条成了"孤儿"，被判删：

    "env":[{"$patch":"delete","name":"SERVER_IP"}]

  • 增改部分 diff(live → 新)：live 1 条 vs 新 1 条，完全相等 → 无事可做，没有"加回"指令。

最终 patch = 两部分取并集 → 只剩下删除指令。$patch: delete 是按 key 删：无论 live 里剩 1 条还是 2 条 SERVER_IP，都会被全部删掉。于是集群侧 SERVER_IP 消失，其它 env 不受影响。

删除部分 diff(旧→新)：旧 2 条 vs 新 1 条 → 多余的判删 → $patch:delete SERVER_IP ──┐
                                                                                 ├→ 并集 → 打在 live(1 条) → 按 key 全删 → 消失
增改部分 diff(live→新)：live 1 条 vs 新 1 条 → 相等，无指令 ──────────────────────┘

↑ 只要旧 manifest 快照里还是 2 条同名 key，删除部分就永远会产生这条 delete 指令。

第二次升级

三组数据：

输入 内容
旧 manifest 快照 1 条（第一次 upgrade 成功后，release Secret 里存的快照已被更新为渲染结果，即干净的 1 条）
新 manifest 1 条
live object 0 条（第一次升级已经把它删光了）

按左右两个 diff 拆开看：

  • 删除部分 diff(旧 → 新)：旧 1 条 vs 新 1 条，相等 → 没有 delete 指令。
  • 增改部分 diff(live → 新)：live 0 条、新 1 条 → 判定"缺了 SERVER_IP，要补上"，生成增补指令（即 $setElementOrder/env 里列出 SERVER_IP + env 补上完整条目）。

最终 patch = 两部分取并集 → 只剩「补上 SERVER_IP」。把它打到 live（0 条）→ 变成 1 条，SERVER_IP 重新出现。

删除部分 diff(旧→新)：旧 1 条 vs 新 1 条 → 相等，无指令 ──────────────────────┐
                                                                        ├→ 并集 → 打在 live(0 条) → 补上 SERVER_IP → 恢复
增改部分 diff(live→新)：live 0 条 vs 新 1 条 → 缺了 → 增补 SERVER_IP ────────┘

为什么第一次升级体现不出"加回"

“加回"这个能力来自右侧的 diff(live → new)；而第一次升级时 live 里的 SERVER_IP 恰好还在（和新 manifest 一致），所以这个 diff 为空、无事可做；真正发令的是左侧的 diff(old → new)——旧快照里那条有罪的"第 2 条同名 SERVER_IP"。也就是说：当时的 live 没有漂移，漂移的是旧快照。这正是"三路"而非"两路"的关键：只有当 live 与 new 不一致时，才会产生"加回/改正"指令；而删不删，则只看 old 与 new 的差异。

五、为什么 --dry-run=server 也看不到"patch”

  • --dry-run=server 只是把阶段 ① 的全量 YAML 丢给 apiserver DryRun 接口做校验。
  • StrategicMergePatch 的计算仍在 Helm 本地完成，客户端不会把"差分"回显给你。
  • 因此你能看到的仍是"全量"而非 patch；若某项被删，全量里就直接没有，看上去就像"消失"。

同理，--post-renderer 作用于阶段 ① 和 ② 之间，看到的也是全量渲染结果，同样看不到最终的 patch。

六、如何亲手抓到真正的 patch

1. 打开 Helm 的 kube-client 调试日志

helm upgrade demo ./chart -n cloud --v=6

日志会输出类似：

2. 审计日志 / 抓包

开启 apiserver 的 Audit 或给 kube-apiserver 抓包，Content-Type 为 application/strategic-merge-patch+json 的 PATCH 体即是最终 patch。

七、Strategic Merge Patch / JSON Merge Patch / Server-Side Apply

Helm 的"三路合并"很容易和 Kubernetes 的另外两个 patch 机制混在一起，需要区分：

机制 特点 Helm 中的角色
Strategic Merge Patch 利用内置类型的 patch strategy / patch merge key，list 按 key 合并 Helm 3 对内置资源的三路合并默认用它
JSON Merge Patch 通用、不知道字段语义，list 常常整体替换 CRD/unstructured 的兜底（见第九节）
Server-Side Apply 服务端 managedFields / field ownership 模型 Helm --server-side 选项（默认 auto）Helm upgrade docs

举例区分 Strategic Merge Patch：只想改 name: app 容器的镜像时，它可以按 name 定位到该容器，而不是把整个 containers 数组整体替换；JSON Merge Patch 则做不到这种精确合并。

排查时先确认当前 Helm 命令是否启用了 --server-side apply，它的字段管理模型与传统的 client-side 三路 patch 不是同一套机制。

八、Helm 3 与 Helm 2 的关键差异

维度 Helm 2 Helm 3
补丁依据 old manifest + new manifest old manifest + live state + new manifest
是否感知集群实时状态 否 是
对 out-of-band 修改 可能忽略或误删 尽量保留不冲突修改
回滚 live drift 可能失败（old 与 rollback target 无差异就"无事可做"） 能看到 live drift 并生成修正 patch
sidecar / webhook 注入 更容易被误删 更容易保留

举例：Deployment 副本数最初是 3，有人 kubectl scale --replicas=0。Helm 2 在 rollback 时若 old 和 rollback target 都是 replicas: 3，会认为"没有差异"而不生成 patch，live 保持 0；Helm 3 看到 old=3、live=0、new=3，会生成 patch 把副本数改回 3 Helm FAQ。Helm 3.0.0 release notes 也把"升级时应用三路 strategic merge patch"列为新特性之一 Helm v3.0.0 release。

九、边界与坑：CRD / unstructured 资源

Helm 3 的三路 strategic merge patch 主要适用于 Kubernetes 内置结构化资源，不一定同样适用于 CRD / unstructured object。

原因是 strategic merge patch 依赖内置类型的结构化 schema 和 Go struct tag 中的 patch strategy 信息；CRD 对 Helm 客户端来说是 unstructured object，缺少这些元数据。

Helm 源码中逻辑会分支处理：对 unstructured / CRD，若启用了三路（threeWayMergeForUnstructured 等），使用 jsonmergepatch.CreateThreeWayJSONMergePatch 和 types.MergePatchType；否则退回普通两路 JSON merge patch Helm client.go。

因此不要简单假设"Helm 3 对所有资源都完全一样地三路 strategic merge"。社区长期讨论此类资源的三路支持：内置资源如 Deployment 会按预期三路合并，但 Istio VirtualService 这类 CRD 可能仍走两路 merge patch Helm issue #9937；相关 PR 也在推进对 unstructured 与 CRD 的三路支持，但需要兼顾兼容性 Helm PR #11650。对 CRD-heavy 的 chart，应结合当前 Helm 版本、选项、资源类型以及是否使用 server-side apply 单独验证。

十、边界与坑：--force / --force-replace

Helm 的三路合并通常通过 PATCH 实现。如果想强制替换，官方 flag 的语义是 “force resource updates by replacement”（Helm 3 为 --force，Helm 4 为 --force-replace）Helm upgrade docs。它采取替换式更新（删除后重建），而不是"先算 patch 再合并"，因此会丢失任何在集群侧做的在线修改（webhook/controller/人工加的字段会被清掉）。

这意味着：

  • 默认 PATCH：倾向于保留 live state 中不冲突的外部修改；
  • force replace：更像"用 Helm 渲染结果替换对象"，容易清掉外部注入的字段。

生产环境不要把 --force* 当成普通升级选项。它适合解决不可变字段变更等特殊问题，但会改变合并语义。

十一、完整例子一：sidecar 保留

假设 Helm chart 原始 Deployment：

# old / new manifest（new 只改了 image tag）
spec:
  template:
    spec:
      containers:
        - name: app
          image: demo:v1   # new 里是 demo:v2

集群中经过 service mesh 注入后，live 变成：

# live state
spec:
  template:
    spec:
      containers:
        - name: app
          image: demo:v1
        - name: istio-proxy
          image: proxy:v1

Converge 后最终 live 为：

spec:
  template:
    spec:
      containers:
        - name: app
          image: demo:v2      # Helm 本次声明的变化
        - name: istio-proxy   # live 里的外部注入，被保留
          image: proxy:v1

三路合并看到：app 从 v1 到 v2 是 Helm 本次声明的变化；istio-proxy 存在于 live 而 old/new 都没有，是外部系统添加的；Deployment 的 containers 是按 name 合并的 list——于是只改镜像、保留 sidecar Helm FAQ。

十二、完整例子二：手工改 replicas 被纠正

# old manifest / # new manifest    # live（被人 kubectl scale 成 0）
spec:                              spec:
  replicas: 3                        replicas: 0

两路 diff 会发现 old 和 new 没有差异，因此不修改 live；三路 diff 会发现 live 与 old/new 不一致，且 replicas 是 Helm 声明字段，于是生成 patch 把副本数改回 3。

这类场景体现三路合并的另一面：它不是盲目保留所有 live drift，而是会把 Helm 管理字段收敛回 Chart 期望状态。

十三、常见误解

  1. 误解一：三路合并会保留所有手工修改 不对。它通常保留"不属于 Helm 声明且不冲突"的 live 修改。如果你手工修改的是 Chart 中明确声明的字段（replicas、image、resources、某个 annotation 值），下次 upgrade 可能把它改回 values/template 渲染出的值。

  2. 误解二：三路合并等于 kubectl apply 不完全等同。二者都涉及三路思想，但 Helm 传统 client-side patch 与 kubectl apply、Server-Side Apply 的字段管理模型不同；Helm 使用 --server-side 后语义又会变化 Helm upgrade docs。

  3. 误解三：Helm 3 对 CRD 一定是 strategic merge patch 不对。CRD/unstructured 缺少 strategic merge 所需的内置类型元数据，历史上可能使用普通 JSON merge patch，甚至仍是两路 merge patch Helm issue #9937、Helm PR #11650。

  4. 误解四：三路合并能解决所有冲突 也不对。它只是降低了误删 live 变更的概率。如果 Helm 和其他 controller（HPA、operator、GitOps）同时管理同一字段，仍会出现"来回覆盖"或升级后被改回的问题。根本解决方式是明确字段 ownership：哪些字段由 Helm 管，哪些由其它 controller 管。

十四、避坑指南 / 生产实践建议

  1. 根本方案：数据源只留一份 不要在 values 和模板里同时 range / 硬编码同名 env；用字典去重或只保留一份数据源。

  2. 模板里显式清空字段 想把不要的 env 清掉而不是删 key，模板里写成：

    - name: SERVER_IP
  value: null

    这样 merge 会识别为"字段清空"，不会误删其它 env。

  3. 不要手工修改 Helm values 中明确声明的字段 要长期变更 replicas、image、resources、env，应修改 values/chart 后 helm upgrade。

  4. 对会被 controller 改写的字段保持克制 不建议 Helm 和 operator 同时写同一个会互搏的字段；明确 ownership 边界。

  5. 谨慎使用 --force* 详见第十节：它是替换语义，会清掉外部注入字段。

  6. CRD 场景单独验证 对 Istio、Argo Rollouts、Prometheus Operator、External Secrets 等 CRD-heavy chart，在测试环境验证 upgrade 后 live object 符合预期。

  7. 用补工具辅助排障 结合 helm get manifest、kubectl get -o yaml、helm diff、--dry-run=server、--v=6 分析，patch 是运行时结合 live state 生成的，单看模板渲染往往推断不出最终 patch。

  8. 避免多个声明式工具管理同一字段 Helm、Argo CD、Flux、kubectl apply、operator、HPA 都在写同一字段时，三路合并只能缓解，不能消除 ownership 冲突。

十六、结语

Helm 的三路合并策略可以概括为：

Helm 3 在升级或回滚资源时，不再只比较"上一次 Helm manifest"和"本次 Helm manifest"，而是同时读取"集群当前 live state"，基于 old、live、new 三者生成 patch。这样既能把 Helm 管理的字段收敛到 Chart 期望状态，又能尽量保留 webhook、controller 或人工添加的不冲突 live 变更。

它的价值主要体现在：

  • 修复 Helm 2 时代忽略 live state 的问题；
  • 避免误删 sidecar、annotation、label 等外部注入内容；
  • rollback 时能纠正 live drift；
  • 更符合 Kubernetes 多 actor 共同修改对象的现实。

但它也有边界：CRD/unstructured 资源的处理历史上不完全等同于内置资源；--force*、server-side apply、多个控制器争抢字段都会改变最终行为。

回到本文开头的问题：当发现"渲染有、集群无"时，九成是合并阶段把字段判为了"删除"。“模板输出 ≠ 最终 patch”，配合 --v=6 等工具，就能把"幽灵消失"的字段抓个现行。
