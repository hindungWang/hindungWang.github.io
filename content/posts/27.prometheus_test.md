# Prometheus性能压测与高可用设计

## Prometheus原理

### 名词

**Series（系列）** 是**指标名 + 一组唯一标签键值对**，对应**一条**时间序列（有序 `(时间戳, 数值)` 点列）。同标签不同指标名是两个 series。如：
```
|<------------------------Series-------------------------->|
avalanche_metric_0_0{cycle_id="0",label_key_0="label_val_0"} 18
```

**Sample（样本）** 是指一个数据点，它包含了一个时间戳和相应的数值。样本是 Prometheus 时间序列数据的基本单位。`<指标名>{<标签集>}` 唯一确定一个 series，series 下每个 `<时间戳> <数值>` 就是一个 sample。如：
```
|<------------------------------Series-------------------->|<--时间戳->|<值>
avalanche_metric_0_0{cycle_id="0",label_key_0="label_val_0"} @125465645  2   -> 一个Sample
                                                             @125465646  5
                                                             ...
```

## Prometheus缺点

原生Prometheus并不支持高可用，也不能做横向扩缩容，当集群规模较大时，单一Prometheus会出现性能瓶颈，无法正常采集数据。

> **表述精确化**：这是 Prometheus 的**设计选择**（单机 TSDB + 生态扩展），而非缺陷。官方不做内置集群，HA 靠部署模式（双实例 + Query 去重）、扩展靠分片（hashmod 抓取分流）或外部组件（Thanos / Mimir / VictoriaMetrics）。

在集群场景下 单一Prometheus只能查询本地的指标，而不能跨区域查询，因此需要一个统一的管理。

## Thanos高可用方案以及性能压测

### Thanos原理

Thanos核心原理就是采用数据冗余的方式，部署多个Prometheus实例，然后将Prometheus产生的数据打散（或者说备份）至每个组件，最后使用ObjectStorage存储起来。
查询时，使用Query组件遍历其他组件将数据清理、合并、打分等操作提供给Query-Frontend。

组件及其功能：[https://thanos.io/tip/thanos/getting-started.md/#get-thanos](https://thanos.io/tip/thanos/getting-started.md/#get-thanos)

#### 总结

停掉一个节点也能保持监控不断，就不必说随机停掉一个POD的结果了，因此，正常情况下Receiver模式能够很好做到HA。

> **方法补全**：本次 HA 演练只验证了"down 节点监控不断"，**未配置 Receiver hashring 副本（replication factor）**——若只做数据打散无副本，挂掉一个 Receiver 节点该段数据在恢复前同样不完整。生产要真正 HA 需配 replication factor，并补"节点恢复后数据补齐"的观测（WAL 回放 → 数据补全）才闭环。

历史数据出现缺失是因为挂掉的节点正好存储了那一部分的数据，没来得及存储到minio，但是不影响最新的数据，等节点启动会恢复该段数据。

> **补充说明（修正）**：这里"引入compactor组件解决"的表述是**错的**。Compactor 的职责是降采样（downsampling）、合并小 block、清理 tombstone、按 retention 删过期数据——**它不负责补数/恢复数据**。
> 数据缺失的真实原因：节点 down 时，WAL 里**尚未固化成 block**（最近约 2h）的数据没来得及上传到对象存储。
> - 节点**只是重启**：WAL 启动时回放，数据自动恢复（Prometheus 崩溃恢复机制）
> - 节点/磁盘**彻底没了**：最近 2h 数据确实丢——需靠 **Receiver 多副本**（remote-write 实时推送 + hashring replication factor）或 **双实例采集 + Query 去重**兜底
> - 取舍：告警实时性场景下，告警评估用的是实时数据，丢失"最近 2h 历史"通常可接受

这是最接近无状态的方法，远程写入具有其他风险和后果，即使崩溃，也会在积极情况下丢失几秒钟的指标数据。

> **表述修正**：Receiver 模式下的采集端 Prometheus **仍然要本地 WAL**（先写本地再 remote-write），不是真正无状态。真正的"轻"是 push-only 场景（avalanche 这类直接 remote-write，或 Prometheus agent mode）。
> 准确表述：Receiver 模式下 Prometheus 本地崩溃只丢几秒（remote-write buffer），因为数据已实时推到 Receiver/对象存储；但 **Receiver 本身是有状态的**——hashring 上某节点挂了，该段数据在恢复前不完整，除非配置了 replication factor（副本）。

*但是使用Receiver模式占用的资源很大，组件多，从监控上看整个HA大概需要30+GiB内存和3+Core CPU*

> **补本质**：Receiver 模式多出的开销来自 remote-write 接收 + hashring 分发 + 更大的 WAL。**选型不是"谁更好"，是看网络拓扑**——Receiver 适合"采集端无法直连对象存储/边缘跨网络"的场景（用副本因子换丢失窗口）；Sidecar 适合"Prometheus 能直连对象存储"的场景（组件少、开销低）。

## Alertmanager HA

由于Alertmanager集群可以做到告警消息的去重(Gossip协议)，因此可以直接对接到多个Prometheus实例，这样就能使用原生的PrometheusRule进行告警规则管理。

> **表述精确化**：Gossip（memberlist）是**同步机制**，去重是它带来的**结果**。准确说：Alertmanager 集群通过 Gossip 协议同步"谁已通知过"的状态和静默（silences），从而实现**同一告警只通知一次（去重）**、多实例静默一致、flapping 抑制。

Thanos提供了一个Ruler组件，用来实现与PrometheusRule相同的功能。因此对于这个集成，两种方案各有利弊：
- 使用PrometheusRule可以与目前现有的业务逻辑相匹配，不用改动太多，但是由于规则是作用在Prometheus本身，因此一般只具有2h的数据（也满足了告警实时要求），对于一些特殊的告警如需要查询多个区域或者很长时间范围的情况就不支持；
- Thanos Ruler可以统一管理各个Prometheus产生的数据并且对接到Alertmanager，缺点就是引入新的组件，维护成本增加

生成svc脚本：
```bash
#!/bin/bash

filename="svcs.yaml"

cat <<EOF > $filename

EOF

for ((i=10001; i<=50000; i++))
do
    name="hxd-sd-$i"

    cat <<EOF >> $filename
---
apiVersion: v1
kind: Service
metadata:
  name: $name
  namespace: hxd-test
  labels:
    app: hxd-test-sd
spec:
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 9001
  selector:
    app: avalanche
EOF

    echo "Added SVC: $name"
done

echo "Generated $filename"
```

生成servicemonitor脚本:
```bash
#!/bin/bash

filename="service-monitors.yaml"

cat <<EOF > $filename

EOF

for ((i=1; i<=1; i++))
do
    name="hxd-sd-$i"

    cat <<EOF >> $filename
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  labels:
    release: hxd-prometheus
  name: $name
  namespace: hxd-test
spec:
  endpoints:
    - path: /metrics
      port: http
  namespaceSelector:
    matchNames:
      - hxd-test
  selector:
    matchLabels:
      app: hxd-test-sd
EOF

    echo "Added ServiceMonitor: $name"
done

echo "Generated $filename"
```
