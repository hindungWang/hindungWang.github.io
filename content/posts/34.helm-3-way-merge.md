## 一、现象复盘

### 1. 安装阶段（helm install）
由于疏忽，我在`values.yaml` 里写上了 `env`，结果在 `deployment.yaml` 模板里 `range` 了一次，结果 YAML 里出现 **同名双份** env：
- 既在 `values.yaml` 里写了
  ```yaml
  env:
    - name: SERVER_IP
      value: "1.2.3.4"
  ```
- 又在 `deployment.yaml` 模板里 `range` 了一次，结果 YAML 里出现 **同名双份** env：
  ```yaml
  env:
  - name: SERVER_IP
    value: "1.2.3.4"
  ...
  - name: SERVER_IP      # 重复
    value: "1.2.3.4"
  ```
- 运行时有效值只认后一条，同时抛警告（警告来自 kubelet 启动容器时）：
  ```
  spec.template.spec.containers[0].env[11]: hides previous definition of "SERVER_IP"
  ```
  注意：这里的"只认一条"是**容器运行时**的最终取值；apiserver 里存的对象可能仍保留两份同名条目——这正是后面 3-way 合并踩坑的根源。无论 live 里剩 1 条还是 2 条（见下文 `$patch: delete` 按 key 删），最终都会消失。

为了消除这个告警消息，我将`values.yaml`里的`SERVER_IP`删掉，但是保留了`template/deployment.yaml`里的`SERVER_IP`。使用`--dry-run`可看到新渲染结果是只存在一个 `SERVER_IP`，符合预期。

然鹅，在第1次执行`helm upgrade`命令升级时，k8s中`SERVER_IP`消失了。同时`--debug`返回的渲染结果的确有一个 `SERVER_IP`。
第二次执行`helm upgrade`命令时，k8s中`SERVER_IP`又出现了，符合预期。


### 2. 疑问
1. 为什么第一次升级 SERVER_IP 会消失？（实际不是 env 全删光，只删了它）
2. `--dry-run=server`、 `--post-renderer` 为何也看不出“被删”的证据？
3. Helm 到底把什么发给了 apiserver？

---

## 二、Helm 渲染与提交的三段流水线

| 阶段 | 内容 | 可见开关 |
| ---- | ---- | -------- |
| ① 模板渲染 | go-template 输出完整 YAML | `--debug`、 `--dry-run`、 `--post-renderer` |
| ② 3-way merge | 本地计算 strategic-merge-patch | **无官方开关**（下文给办法） |
| ③ 调用 K8s | 把 patch/apply 发给 apiserver | `--v=6` 可打印 PATCH 体 |

---

## 三、3-way merge 到底在合并什么

Helm 取三份数据：

1. **旧 manifest**（上一次 release 存在 Secret 里）
2. **新 manifest**（阶段 ① 的输出）
3. **live object**（当前集群真实状态）

但它**不是**把三份数据互相 diff，真实机制是：

```
old manifest −(两路求差)→ 生成 strategic-merge-patch ──→ 打到 live object 上
```

即：**拿旧 manifest 与新 manifest 算出一个差分包（strategic-merge-patch），再把这个补丁作用在 live 上**。patch 里不只是"值"，还带语义操作：

- `$setElementOrder/xxx`：标定列表项顺序
- `$patch: delete`：**按 merge key 删除**（不是按条目）
- `value: null`：清空字段

关键点：**env 这类列表是按"合并键"（merge key = `name`）来合并的**，不是按"有没有"判断的。所以判定规则要更精确地写成：

- 新 manifest 有、旧没有 → **新增**
- 旧里某 merge key 在新里**配不上一对一**（比如旧里同名 2 份、新里同名 1 份）→ 判定为"用户删了多余那个" → 生成 `$patch: delete`
- 新旧 key 能配对 → 逐字段合并
- 三份数据的差别只影响"新 manifest 的动态值"，**最终结果 = patch 打在 live 上**，因此才会出现"渲染有、集群无"这类漂移。

**第一次升级时：**

- 旧 manifest 快照里：**2 条** `name: SERVER_IP`（values 一份 + 模板 range 一份）
- 新 manifest：**1 条** SERVER_IP
- 按 merge key 配对：新的 1 条与旧的第 1 条配对，旧的多出来的第 2 条成了"孤儿" → 合并判定为"用户不要多余的这条"，于是产生
  ```json
  "env":[{"$patch":"delete","name":"SERVER_IP"}]
  ```
- `$patch: delete` 是**按 key 删**：无论 live 里剩 1 条还是 2 条 `SERVER_IP`，都会被**全部删掉**。
- 最终 apiserver 收到的是 **"把 name=SERVER_IP 的项全部摘掉"**，于是集群侧 SERVER_IP 消失，其它 env 不受影响。

```
旧 manifest 快照(2 条同名 SERVER_IP) ──┐
                                       ├─ 两路求差 ─→ 判"多余的 SERVER_IP 要删"
新 manifest (1 条，修复后) ────────────┘
                                       │
              $patch:delete SERVER_IP ─┤ 打在 live 上 → 按 key 全删 → 消失
live object (1 条) ────────────────────┘
```
↑ 只要旧 manifest 快照里还是 2 条同名 key，就永远会产生这条 delete 指令。

**第二次升级时：**

- 第一次 upgrade 成功后，release Secret 里的旧快照已被更新为**修好的 1 条**，不再产生 delete 指令。
- 而 3-way 合并的语义是"新 manifest 有、live 没有"的项会被**加回**——这就是三路与两路 diff 的本质区别：不是"old == new 就不动"，而是**能自动修复集群侧漂移**。
- 于是 SERVER_IP 重新出现，符合预期。

```
第一次后 live(0 条) ──┐
                      ├─ 新名单里 SERVER_IP 在旧里也有 → 不再判删 → 恢复
旧快照已更新(1 条) ────┤
新 manifest (1 条) ────┘
```

## 四、为什么 `--dry-run=server` 也看不到“patch”

- `--dry-run=server` 只是把 **阶段 ① 的全量 YAML** 丢给 apiserver **DryRun** 接口做**校验**。
- StrategicMergePatch 的计算仍在 **Helm 本地完成**，客户端不会把“差分”回显给你。
- 因此你能看到的仍是“全量”而非 patch；若某项被删，全量里就**直接没有**，看上去就像“消失”。

## 五、如何亲手抓到真正的 patch

### 1. 打开 Helm 的 kube-client 调试日志
```bash
helm upgrade demo ./chart -n cloud --v=6
```
日志会输出类似

`application/strategic-merge-patch+json` 的 PATCH 体即是最终 patch。

## 六、避坑指南

1. **根本方案**  
   不要在 values 和模板里同时 `range` / 硬编码同名 env；用字典去重或只保留一份数据源。

2. **想“强制覆盖”而非“合并”**  
   模板里显式把不要的 env 置 `null`：
   ```yaml
   - name: SERVER_IP
     value: null
   ```
   这样 merge 会识别为“字段清空”，不会误删其它 env。

3. **需要跳过 3-way merge**  
   升级时加 `--force`（Helm 3），Helm 走的是"删除 + 重建（replacement strategy）"，并不会直接 PUT 全量对象绕过合并（Helm 没有这个开关；`--force` 只是先删后建，仍会丢现场改动）；  
   ⚠️ 会丢失任何在集群侧做的在线修改，生产慎用。

## 八、结语

Helm 的 `--debug` / `--dry-run` 只能让你看到“模板长什么样”，**真正的 diff 发生在本地 3-way merge**。  
当发现“渲染有、集群无”时，九成是合并阶段把字段判为“删除”。  
 **“模板输出 ≠ 最终 patch”**，配合 `--v=6` 等工具，就能把“幽灵消失”的字段抓个现行。
